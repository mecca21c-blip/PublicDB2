## 2. APP PURPOSE

PublicDB1은 시민 민원 라우팅 앱이 아니라, 정부·공공기관이 공식 공개한 다음 정보를 수집하고 증거·이력과 함께 유지하는 로컬 DB 관리 시스템이다. [PROJECT_SCOPE.md](C:/PublicDB/docs/PROJECT_SCOPE.md:3)

핵심 데이터는 다음과 같다.

- 기관 `Agency`와 상위 기관 관계
- 계층형 부서·조직 `OrgUnit`
- 업무 `Duty`
- 사람 `Person`과 재직·소속 `PersonAssignment`
- 전화·이메일·팩스 등의 `ContactPoint`
- 공식 URL `Source`, 수집 방법·형식·범위 정책
- 수집 실행 `CrawlRun`, 원문 증거 `Observation`
- 연락처·직원명부 추출 후보
- Master 데이터와 증거를 잇는 `SourceOccurrence`
- 변경 감지 후보, 최종 변경 사건, 연락처 이력

모델 근거: [source.py](C:/PublicDB/app/models/source.py:30), [agency.py](C:/PublicDB/app/models/agency.py:15), [org_unit.py](C:/PublicDB/app/models/org_unit.py:15), [duty.py](C:/PublicDB/app/models/duty.py:12), [person.py](C:/PublicDB/app/models/person.py:12), [contact.py](C:/PublicDB/app/models/contact.py:19), [observation.py](C:/PublicDB/app/models/observation.py:22).

현재 주요 사용자 흐름은 두 종류로 분리되어 있다.

1. 웹 UI: Source 운영 현황 조회 → 단일 Source 등록 → 대시보드 재조회
2. CLI/서비스: 기관 등록 → Source 연결 → 단일 URL 수집 → 추출 → Master 계획/반영 → 변경 감지

웹 UI는 두 번째 흐름을 시작하거나 승인하는 통합 관리 화면이 아니다.

### 단계별 성공 의미

- 접속 성공: HTTP 2xx이고 크기 제한을 통과한 경우에만 가능하다. 비-2xx는 `FAILED`. [http_fetcher.py](C:/PublicDB/app/collectors/http_fetcher.py:86)
- 저장 성공: RAW 파일 저장 후 Observation과 CrawlRun을 DB에 commit해야 `SUCCESS`. [collection_service.py](C:/PublicDB/app/services/collection_service.py:112)
- 추출 성공: 별도 CLI/서비스 실행이 필요하며, 수집 성공이 추출 성공을 뜻하지 않는다.
- 화면 반영 성공: 대시보드가 DB의 기존 상태를 읽는 별도 단계다. 수집·추출·변경 감지 후 자동 push는 없으며 재조회 시 표시된다.
- Master 반영 성공: 추출 후보 생성과 별개이며 명시적인 apply가 필요하다.

| C. URL 엑셀 일괄 업로드 | `XLSX`는 데이터 형식 enum/선택지일 뿐 업로드 기능이 아님 | 파일 선택, 파싱, 컬럼 매핑, 미리보기, 일괄 저장 전부 미구현 |
| D. 파일·기존값 중복/충돌 | 단건 URL 정규화와 기존 Source 충돌 검사는 있음 | 파일 내부 중복, 행별 충돌, 기관·부서 충돌, 일괄 결과 보고 없음 |
| E. 자료없음/오류/미확인 URL | 수집 상태와 일부 단계별 실패 모델은 있음. UI에는 `정상/실패/진행 중/미수집/비활성/부분 완료`만 표시 | `자료없음` 전용 상태가 없고, 접근 성공·추출 실패·미지원·미검사를 한 화면에서 구분하지 못함 |
| F. URL 검토·제외·삭제 | Source에 `active` 필드는 있으나 이를 변경하는 UI/API/CLI가 없음 | 검토 큐, 제외 사유, 비활성화, 복구, 삭제 영향 확인 모두 미구현 |

### 질문별 결론

- 기관/부서가 다를 때 동일 URL:
  `normalized_url`이 전역 `unique=True`다. [source.py](C:/PublicDB/app/models/source.py:36) 따라서 같은 URL은 다른 기관으로 별도 등록할 수 없고, 기존 기관과 다른 `agency_id`로 요청하면 충돌한다. [source_administration_service.py](C:/PublicDB/app/services/source_administration_service.py:148)

- 0건을 무조건 자료없음으로 처리하는가:
  아니다. `자료없음` 상태 자체가 없다. 연락처/명부 extractor는 정상 처리 결과가 0건이어도 추출 실행을 `SUCCESS`로 저장할 수 있다. 반면 변경 감지는 직원명부 record가 0건이면 실행을 거부한다. [source_change_detection_service.py](C:/PublicDB/app/services/source_change_detection_service.py:215)

- 접근 실패·추출 실패·미지원·미검사 구분:
  DB 내부에서는 일부 구분된다. `CrawlRun`, `ExtractionRun`, 오류 요약과 미수집 상태가 별도로 존재한다. 그러나 Source 표의 상태 계산은 최신 `CrawlRun`만 보므로, 접근 성공 뒤 추출 실패·0건·미검사를 표시하지 않는다. [dashboard_query_service.py](C:/PublicDB/app/web/services/dashboard_query_service.py:509) API/크롤링/파일/문서는 등록할 수 있지만 collector가 없어 계속 `미수집`으로 보일 수 있다.

- URL 삭제 영향:
  삭제 기능이 없다. ORM 관계와 FK에는 destructive cascade 및 `ON DELETE`가 의도적으로 없다. [test_models.py](C:/PublicDB/tests/test_models.py:289) 따라서 기존 Observation·수집 이력·출처 관계를 자동 삭제하는 계약도 없다. 의존 데이터가 있는 Source의 물리 삭제는 일반적으로 FK에 의해 거부될 구조지만, 실제 삭제 서비스가 없으므로 정확한 제품 동작은 미정이다.

## 6. UI 설계에 영향을 주는 사실

- Source와 기관은 다대일이지만 Source와 부서의 직접 관계는 없다.
- 하나의 기관은 API·웹페이지·파일·문서 등 여러 Source를 가질 수 있도록 설계되어 있다. [ARCHITECTURE.md](C:/PublicDB/docs/ARCHITECTURE.md:133)
- Source 역할, 수집 방법, 데이터 형식은 독립 차원이다. 등록 가능한 방법이 실제 수집 가능한 방법이라는 뜻은 아니다.
- Source 등록은 수집을 시작하지 않는다. UI에도 이 사실이 명시되어 있다. [dashboard.html](C:/PublicDB/app/web/templates/dashboard.html:121)
- 발견 후보와 Master 확정값은 의도적으로 분리된다.
- 연락처의 Master 승격은 기관·부서·업무 문맥을 요구하며, 사람과 연결된 연락처 승격은 현재 완성되지 않았다.
- `UNKNOWN`과 `ADDITIVE_ONLY` coverage에서는 누락 후보를 만들지 않는다. `COMPLETE_SNAPSHOT`에서만 같은 Source의 과거 증거에 대해 missing 후보를 만든다. [source_change_detection_service.py](C:/PublicDB/app/services/source_change_detection_service.py:304)
- missing 후보는 자동 비활성화나 삭제가 아니다.
- 현재 검토 대기 화면은 집계만 제공하는 mock에 가까우며 실제 검토 작업 공간이 아니다.
- 과거 조직도·기관 흐름 UI는 승인된 현재 UI가 아니며, 지역 지도는 당시에도 placeholder였다.
- README/ROADMAP 일부는 현재 구현보다 오래되어 구현 여부 판단 근거로 단독 사용하면 안 된다.
