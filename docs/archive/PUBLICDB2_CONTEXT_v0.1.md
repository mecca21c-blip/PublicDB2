# PublicDB2 — 프로젝트 컨텍스트 v0.1

작성일: 2026-09-29
문서 상태: DRAFT / 화면·기능 합의용
전체 UI Freeze: 미완료
Production 기능 구현 승인: 아직 없음

## 1. 이 패키지의 용도

PublicDB1의 실제 구현 현황과 PublicDB2의 새 UI 방향을 한곳에 남기기 위한 초안이다.
완성된 구현 계약이 아니며, 이 패키지를 받았다는 사실만으로 새 기능 구현이나 기존 코드 이식을 시작하지 않는다.

현재 대시보드 이미지의 시각적 방향은 사용자가 긍정적으로 평가했다.
이를 전체 메뉴·버튼·데이터·기능·레이아웃 상세까지 승인한 것으로 확대 해석하지 않는다.
다른 탭의 이미지와 주요 입력·검토·실패 상태는 아직 승인되지 않았다.

## 2. 프로젝트 식별

| 항목 | 경로 / 값 | 취급 |
|---|---|---|
| 새 프로젝트 | `C:\PublicDB2` | PublicDB2의 작업 루트 |
| 기존 프로젝트 | `C:\PublicDB` | PublicDB1, 읽기 전용 참고 |
| 새 원격 저장소 | `https://github.com/mecca21c-blip/PublicDB2.git` | 사용자 생성. 이 문서 작성으로 연결·업로드되지 않음 |
| 감사 대상 HEAD | `1319ae31ddf7234a1a8632271b5ff899006d47de` | 00A 보고서 기준, 이후 변경은 별도 확인 |

PublicDB2 폴더에 Git이 없다는 사유로 PublicDB1의 읽기 전용 분석을 막지 않는다.
기존 소스 Git 조회는 `git -C C:\PublicDB ...`처럼 대상을 명시한다.
이 패키지는 어떤 Git 작업·DB 연결·앱 실행도 수행하지 않는다.

## 3. 제품 목적과 현재 증거

목적: 정부·공공기관이 공식 공개한 기관·조직/부서·업무·사람/재직·연락처를
공식 출처, 수집 증거, 변경 이력과 함께 유지하는 로컬 DB 관리 시스템.

근거: `evidence/PUBLICDB1_INVENTORY_00A.txt`, §2 및 §4.

00A가 확인한 중요한 경계:
- 실제 활성 웹 화면은 대시보드 하나다. 다른 메뉴는 비활성이다.
- 일부 기능은 CLI/서비스로 존재하지만 웹 UI에 연결되지 않았다.
- 00A는 읽기 전용 감사다. 테스트 실행이나 실환경 동작 검증을 수행하지 않았다.
- 따라서 '구현 존재'를 '실제 정상 동작 검증 완료'라고 표시하지 않는다.
- 현행 기술 스택은 Python/FastAPI/Jinja2/JavaScript/CSS/SQLAlchemy/SQLite 계열이다.
  새 그림의 외형이 React, Tauri 등의 기술 스택 전환을 승인하는 것은 아니다.

## 4. 사용자 확정 요구사항

- 기존 앱 전체에 패치를 덧대는 대신 새 프로젝트로 계승한다.
- 실제 정상 동작을 확인한 자산을 선별 계승하고 미구현 기능은 새 UI에 연결해 완성한다.
- UI와 기능 범위를 먼저 확정하고, 그 합의를 Markdown/컨텍스트로 프로젝트에 둔다.
- 기관명 직접 입력을 지원한다.
- 기관/부서별로 여러 수집 URL을 관리한다.
- 소스 URL 목록을 Excel로 일괄 업로드하고 중복을 검출한다.
- 자료없음, 오류, 미확인 URL을 구분한다.
- 불필요한 URL을 사용자가 검토하고 정리·삭제할 수 있어야 한다.
- 실제 코딩은 Codex가 담당한다.
- 실행 지시문은 작업에 맞는 정확한 엔진 버전·추론 강도를 명시한 하나의 블록으로 전달한다.
- 사용자의 결정 사항과 앱 실행 후 확인 항목은 실행 지시문 밖에서 구분한다.

## 5. 문서 역할과 우선순위

| 자료 | 역할 |

| `DECISIONS.md` | 사용자 확정사항 / 제안 / 미결정사항 구분 |
| `UI_SPEC.md` | 화면별 구성·동작·상태·전환의 초안 |
| `FEATURE_MAP.md` | 기존 코드와 새 화면의 연결 지도, 검증 수준 |
| `design/01-dashboard-reference-v0.1.png` | 시각적 방향 참고. 실행 데이터·기능의 근거가 아님 |
| `evidence/PUBLICDB1_INVENTORY_00A.txt` | 사용자가 전달한 Codex 감사 원문 |

승인된 문서 계약이 그림의 예시 데이터보다 우선한다.
서로 충돌하면 임의 보완하지 않고 충돌 항목을 보고한다.
지금은 전체가 초안이므로 구현 지시문에서 따로 범위와 승인을 정해야 한다.

## 6. 기준 이미지 주의

사용할 이미지: 두 번째로 생성된 어두운 사이드바의 PublicDB2 대시보드.
원본 크기: 1536 × 1024.

첫 번째 밝은 사이드바의 '소스 관리 대시보드' 이미지는 이 패키지에 포함하지 않았다.

다음은 기준 이미지에 있더라도 제품 계약이 아니다.
- 기관 수, 연락처 수, 수집 건수, 날짜, 상태, 증감률, 차트 값
- 예시 기관명, URL, '보도자료/공지사항' 같은 예시 소스명
- 관리자 계정, 알림, 빠른 등록의 미정 동작
- 사이드바의 메뉴 개수와 분리 수준

실제 제품의 예시 소스는 직원안내·담당업무·조직도·부서 연락처 등 목적에 맞게 정리한다.
디자인 목업 데이터는 DEMO임을 분명히 하고 production 저장소에 넣지 않는다.

## 7. 진행 순서

1. 이번 패키지를 기준으로 탭별 화면 시안과 기능 범위를 논의한다.
2. 수집 소스 → 연락처 DB → 검토 대기 순으로 핵심 운영 화면부터 구체화한다.
3. 기관·조직/부서·업무, 이력·변경, 통계·설정 화면을 같은 스타일로 설계한다.
4. 주요 폼·미리보기·중복·오류·빈 상태·삭제 영향 화면을 확정한다.
5. 전체 UI와 기능 범위, 지원/미지원 표시를 문서에 승인 상태로 기록한다.
6. Codex가 승인된 UI만 먼저 구현하고 사용자가 실제 화면을 비교 확인한다.
7. 기존 기능을 필요한 범위에서 검증·분리해 연결하고 부족한 기능을 구현한다.
8. UI에서 수집·추출·검토·확정·내보내기의 사용자 흐름을 검증한다.

단계 1~5가 완료되기 전에 Codex에게 나머지 탭을 자유롭게 설계하게 하지 않는다.
UI 구현 단계는 실제 수집·추출·DB 변경의 승인으로 간주하지 않는다.

## 8. 사용자 검수와 에이전트 검증

사용자: 화면별 정보 우선순위, 목록 가독성, 상세/팝업, 창 크기 변화, 실제 클릭 흐름을 확인.
Codex: 승인된 범위의 정적 검사·테스트·빌드·headless 동작과 계약 일치를 확인.
이번 문서 작성 단계에는 앱 실행이나 수집 재실행이 필요하지 않다.
